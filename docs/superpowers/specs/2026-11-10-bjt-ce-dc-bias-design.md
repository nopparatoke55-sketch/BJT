# BJT Common-Emitter DC Bias Web App — Design (ฉบับสั้น)

วันที่: 2026-11-10

สถานะ: อนุมัติแล้ว (2026-11-10) — แนวทาง A

## 1. เจตนา และเหตุผล (Intent & Why)

นักศึกษาต้องส่งแลปสั้นที่เป็น **เว็บแอป Flask จริง** ไม่ใช่สคริปต์ CLI
เป้าหมายคือให้นักศึกษาเห็นว่าเครื่องมือคำนวณที่ใช้สอบ/ทำรายงานนั้น
คำนวณจุดทำงานกระแสตรง (DC operating point) ของวงจรไบอัสแบบแบ่งแรงดัน
ได้ถูกต้อง และ **พิสูจน์ได้ด้วยการคำนวณอีกวิธีหนึ่งที่เป็นอิสระจากกัน**

คุณค่าหลักของแลปคือ *ความน่าเชื่อถือของตัวเลข* ไม่ใช่ความสวยของหน้าจอ
ดังนั้นทุกอย่างที่เกินจาก DC bias ถูกตัดออกโดยเจตนา

## 2. Goals

1. รับค่า `VCC, R1, R2, RC, RE, beta, VBE` จากฟอร์มเว็บ
2. คำนวณ `IB, IC, IE, VB, VC, VE, VCE` พร้อมหน่วย (A/mA/µA, V)
3. ตรวจสอบอินพุตและแจ้งข้อผิดพลาดเป็นรายฟิลด์
4. ระบุขอบเขตการทำงาน: active / cutoff / saturation พร้อมคำเตือน
5. คำนวณซ้ำด้วยวิธีที่สอง (nodal 2×2) แล้วเทียบผลให้เห็นบนหน้าเว็บ
6. มีเทสต์อัตโนมัติที่รันจริง และแอปรันได้บน localhost

## 3. Non-goals (ตัดออกชัดเจน)

- ไม่มี AC analysis, phasor, Bode plot, frequency response
- ไม่มี transient / time-domain / waveform / function generator
- ไม่มี schematic editor, การลากวางอุปกรณ์, การจำลอง SPICE
- ไม่มี FET / MOSFET / op-amp / วงจรหลายสเตจ
- ไม่มี database, login, การบันทึกประวัติ, export PDF/CSV
- ไม่มีกราฟ, animation, dark mode, ไลบรารี UI ภายนอก
- ไม่แตะ `electrical.py` และ `test_electrical.py` (งานอีกใบ)

## 4. Anti-goals (ทำงานได้แต่ถือว่าล้มเหลว)

- หน้าจอสวยแต่ backend เรียกค่าคงที่หรือ hardcode ผลลัพธ์
- เทสต์ที่ผ่านเพราะ assert ค่าที่เขียนตามผลลัพธ์ตัวเอง (tautology)
- "independent calculation" ที่เรียกฟังก์ชันเดียวกันซ้ำ
- แผนงานยาวเกินกว่าจะทำเสร็จในคาบแลป

## 5. Constraints

- Python 3.12.7 (มีอยู่), Flask + pytest ยังไม่ติดตั้ง → ต้องสร้าง `.venv`
- รันบน Windows, เข้าผ่าน `http://127.0.0.1:5000`
- ต้อง commit ขึ้น GitHub วันนี้ (branch `main`, remote มีอยู่แล้ว)
- ไฟล์ README.md ปัจจุบันมี merge-conflict marker ค้างอยู่ (ปัญหางานอื่น)
  → แลปนี้ **ไม่แก้** และไม่ผูกกับการ commit ของงานนี้

## 6. Approaches ที่พิจารณา

| # | แนวทาง | ข้อดี | ข้อเสีย |
|---|--------|-------|---------|
| A | Thevenin ที่เบส + ตรวจทานด้วย nodal 2×2 | ตรงตำรา, โค้ดสั้น, พิสูจน์ความถูกต้องของโค้ดได้ | ผลต่างเป็น ~0 ทำให้รายงานดูไม่ตื่นเต้น |
| B | เทียบ exact base-loading กับ stiff-divider approximation | เห็นความไวของโมเดล 1–3 % | ไม่มีคำตอบไหน "ถูก" คนอ่านสับสน |
| C | แก้สมการ nonlinear (Ebers–Moll) แบบ iterative | แม่นที่สุด | เกินขอบเขตแลป DC bias อย่างชัดเจน |

**เลือก A** — ตรงกับถ้อยคำ "verify results" ในใบแลป, ขอบเขตเล็กที่สุด,
และยังคงเป็นวิธีคำนวณที่แยกเส้นทางโค้ดกันจริง (closed-form vs. matrix solve)

```
docs/superpowers/specs/... # เอกสารนี้
```

### 7.2 สูตร — วิธีที่ 1 (closed form, Thevenin)

```
VBB = VCC · R2 / (R1 + R2)
RB  = R1 · R2 / (R1 + R2)
IB  = (VBB − VBE) / (RB + (1 + β)·RE)
IC  = β · IB
IE  = (1 + β) · IB
VB  = VBE + IE · RE
VC  = VCC − IC · RC
VE  = IE · RE
VCE = VC − VE
```

### 7.3 สูตร — วิธีที่ 2 (nodal, แก้ระบบ 2×2)

ไม่ทราบค่า: `VB, IB`

```
(1/R1 + 1/R2)·VB + IB        = VCC/R1        (KCL ที่โหนดเบส)
VB − (1+β)·RE·IB             = VBE           (รอยต่อ BE + RE)
```

แก้ด้วย Gaussian elimination แบบ 2×2 (เขียนเอง ไม่ใช้ numpy)
แล้วต่อด้วย `IC = β·IB`, `IE = (1+β)·IB`, `VC = VCC − IC·RC`,
`VE = IE·RE`, `VCE = VC − VE`

วิธีที่ 2 ใช้สมการคนละชุดและเส้นทางโค้ดคนละอันกับวิธีที่ 1
ถ้าพีชคณิตในวิธีที่ 1 พิมพ์ผิด จะเห็นผลต่างทันที
**ยอมรับว่าทั้งสองวิธีให้ผลตรงกันถึงระดับ ~1e-12 เพราะเป็นฟิสิกส์เดียวกัน
— มันคือการตรวจโค้ด ไม่ใช่การตรวจโมเดล**

### 7.4 การจำแนกขอบเขต

| เงื่อนไข | Region | การแสดงผล |
|----------|--------|-----------|
| `VBB ≤ VBE` | cutoff | `IB = IC = IE = 0`, `VCE = VCC`, `VB = VBB`, `VC = VCC`, `VE = 0` + คำเตือน "ทรานซิสเตอร์ตัดการทำงาน (VBB ≤ VBE)" |
| `VCE < 0.3 V` | saturation | แสดงค่าที่คำนวณได้ + คำเตือน "อยู่ในโซนอิ่มตัว ค่า VCE จากโมเดลใช้ไม่ได้" |
| อื่นๆ | active | แสดงค่าปกติ ไม่มีคำเตือน |

ทั้งสองวิธีใช้เกณฑ์เดียวกัน จึงเทียบกันได้เสมอ

### 7.5 Validation (ฝั่งเซิร์ฟเวอร์เป็นหลัก)

| ฟิลด์ | กติกา | ข้อความเมื่อผิด |
|-------|-------|-----------------|
| VCC | ตัวเลข, > 0, ≤ 100 | "VCC ต้องมากกว่า 0 และไม่เกิน 100 V" |
| R1, R2 | ตัวเลข, > 0 | "R1 ต้องมากกว่า 0 Ω" |
| RC | ตัวเลข, ≥ 0 | "RC ต้องไม่ติดลบ" |
| RE | ตัวเลข, > 0 | "RE ต้องมากกว่า 0 Ω" |
| beta | ตัวเลข, > 0 | "β ต้องมากกว่า 0" |
| VBE | ตัวเลข, 0 < VBE < 1 | "VBE ต้องอยู่ระหว่าง 0 ถึง 1 V" |

- ค่าที่ไม่ใช่ตัวเลข → error รายฟิลด์ ไม่ throw 500
- ฟอร์มเดิมต้องคงค่าที่ผู้ใช้กรอกไว้หลัง error
- ฟอร์มว่าง (GET) → แสดงค่าเริ่มต้นตัวอย่าง VCC=12, R1=47k, R2=10k,
  RC=2.2k, RE=470, β=150, VBE=0.7

### 7.6 Routes

| Method | Path | ทำอะไร |
|--------|------|--------|
| GET | `/` | แสดงฟอร์มพร้อมค่าเริ่มต้น |
| POST | `/calculate` | validate → คำนวณ 2 วิธี → render ผลลัพธ์ |

ไม่มี API/JSON, ไม่มี redirect (ไม่ใช้ PRG) — เล็กที่สุดที่ใช้งานได้

### 7.8 เกณฑ์ตรวจรับ (Acceptance Criteria)

ทุกข้อต้องพิสูจน์ได้ด้วยคำสั่งที่รันจริง:

1. `pytest` ผ่านทั้งหมด และมีจำนวนเทสต์ ≥ 15
2. เทสต์คณิตศาสตร์ครอบคลุม: active, cutoff, saturation, ค่าขอบ, ค่าผิดรูป
3. `test_bjt.py` ยืนยันตัวเลขกับค่าที่คำนวณมือไว้ล่วงหน้า (ไม่ใช่ assert จากผลรัน)
4. `test_bjt.py` ยืนยัน `|วิธี1 − วิธี2| < 1e-9` สำหรับทุกเคสที่ถูกต้อง
5. `test_app.py` ยืนยัน: `GET /` = 200, `POST` ค่าถูก = 200 + มีตัวเลข,
   `POST` ค่าผิด = 200 + ข้อความ error, ไม่มี 500
6. รัน `python app.py` แล้วเปิด `http://127.0.0.1:5000` ได้จริง (สาธิตสด)
7. `bjt.py` ไม่ import Flask; `app.py` ไม่มีสูตรฟิสิกส์
8. commit ขึ้น GitHub สำเร็จ ≥ 1 commit ที่มีข้อความสื่อความ

## 8. สิ่งที่เหลือให้ผู้ลงมือตัดสินใจ

- จำนวนทศนิยม/รูปแบบหน่วย (เลือก: 3–4 significant digits + หน่วยอัตโนมัติ)
- ภาษา UI: อังกฤษพร้อมสัญลักษณ์มาตรฐาน (เปลี่ยนเป็นไทยได้ทีละ template)
- ชื่อตัวแปร/โครง dataclass ภายใน `bjt.py`
- รายละเอียด CSS (เป้าหมาย: อ่านง่าย ตารางตรง ไม่มี framework)
